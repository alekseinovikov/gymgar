# CLAUDE.md: руководство для агентов и контрибьюторов

**Gymgar** — нативное desktop-приложение на Rust для редактирования силовых тренировок (упражнения, тренировки, подходы, программы). Оно само синхронизируется с Garmin Connect и предоставляет MCP-сервер, чтобы агенты могли делать всё то же, что пользователь делает в UI.

- **Только Rust.** UI на egui/eframe поверх wgpu. Никаких Tauri, Electron, webview или JS/TS.
- **Имя:** в пользовательском тексте пишем **Gymgar**. Машинные имена в нижнем регистре: крейты `gymgar-*`, бинарь `gymgar`, app id `gymgar`.
- **Откуда подход:** структура и практики взяты из [storytold/photocraft](https://github.com/storytold/photocraft). Что именно взяли, что сделали иначе и какие решения ещё открыты, описано в [`docs/architecture.md`](docs/architecture.md). Прочитай его перед первой задачей.

## 1. Карта воркспейса

```text
crates/
  domain       L0  модель: упражнения, тренировки, подходы, программы, единицы (чистые данные, без I/O)
  garmin       L0  standalone-клиент Garmin Connect: auth, workouts, activities (свои DTO, без workspace-зависимостей)
  store        L1  локальное хранилище доменной модели: схема, миграции, атомарные записи
  sync         L2  маппинг domain ⇄ Garmin, отслеживание изменений, разрешение конфликтов
  engine       L3  Session + реестр команд (каждое действие — команда), история/undo, фоновые задачи
  ui-egui      L4  egui-оболочка (тонкая: все действия идут через engine)
  automation   L4  MCP-сервер (rmcp) поверх реестра команд
apps/
  gymgar           desktop-приложение (eframe): окно, логи, платформенные сервисы, сборка всего вместе
  gymgar-cli       (появится вместе с MCP) headless CLI: `gymgar-cli mcp`, sync, импорт/экспорт
xtask/             cargo xtask ci | layers
```

**Слои проверяет `cargo xtask layers`** (`xtask/src/layers.rs` читает `cargo metadata`):

- крейт зависит только от крейтов **более низкого** слоя: без циклов и без зависимостей «вбок»;
- standalone-крейт (`garmin`) не зависит ни от одного крейта воркспейса, поэтому маппинг живёт в `sync`;
- UI-тулкит (egui, eframe, winit, wgpu, rfd, egui_extras, egui_plot) разрешён только в `ui-egui` и `apps/*`;
- новый крейт регистрируется в `TABLE` в `xtask/src/layers.rs`, иначе проверка падает.

Сейчас библиотеки — заготовки, в каждой только `//!`-описание ответственности. Наполняются по мере появления фич.

## 2. Золотые правила

### Never crash (важнее любой фичи)

Пользователь доверяет приложению свои тренировки, и паника означает потерянные данные. Битый ответ Garmin, неверные MCP-параметры, испорченный файл, пропавшая сеть или полный диск должны давать понятную ошибку, а не панику.

- **Не-тестовый код не паникует.** Запрещены `unwrap`, `expect`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` и индексация `[i]`. Возвращай ошибку крейта и пробрасывай её через `?`. Используй `ok_or(..)?`, `let .. else`, `get()`. `unwrap_or*` допустим только там, где fallback действительно корректен; fallback, который тихо портит данные, недопустим. Незавершённая функциональность возвращает ошибку «unsupported». Единственное исключение — доказуемо безошибочный литерал: `#[allow(clippy::expect_used)]` плюс `.expect("почему это не упадёт")`.
- **Это проверяется автоматически:** `[workspace.lints.clippy]` в `Cargo.toml` ставит `deny`, а `clippy.toml` ослабляет правила только внутри тестов.
- **`unsafe` запрещён** (`unsafe_code = "forbid"`).
- **Внешние данные враждебны** (Garmin, MCP, файлы, ввод в UI). Для длин и счётчиков используй `checked_*` и `saturating_*`. Защищайся от деления на ноль и от NaN/inf. Ограничивай аллокации, размер которых пришёл извне. Строки режь только по границам символов.
- **Не допускай каскадов.** При отравлении мьютекса используй `lock().unwrap_or_else(PoisonError::into_inner)`. `join()` потока возвращает `Result`, обрабатывай его.
- **Последний рубеж.** Приложение ловит панику вокруг диспетчеризации команд и фоновых задач и превращает её в ошибку; `panic = "unwind"` не меняем. Это страховка, а не разрешение паниковать.
- **Докажи фикс.** Каждое исправление краша идёт вместе с регрессионным тестом, который падал до исправления.

### 1. Всё — команда

Любое пользовательское действие — это команда в `engine` со стабильным id вида `area.action` в camelCase: `workout.create`, `workout.addExercise`, `exercise.rename`, `garmin.sync`, `garmin.workout.push`. UI, CLI и MCP вызывают **одну и ту же** точку входа `Session::execute(id, params)`. Только чисто визуальное состояние (выбранная вкладка, ширина панели, прокрутка) живёт в UI, а не в engine.

Команда описывается `CommandSpec`: `id`, `label`, путь в меню, хоткей, **типизированные параметры**, `enabled` (с причиной, почему команда сейчас недоступна), `run`, вид (query, мутация или фоновая задача) и флаг «можно ли вызывать агенту». Мутация записывает ровно **один шаг истории** (undo). Серию мелких правок (перетаскивание, набор текста) склеивай через `coalesce`.

### 2. Параметры команд типизированы (здесь мы отличаемся от photocraft)

У photocraft параметры — свободный `serde_json::Value` плюс строка-описание, и проверку опечаток в ключах им пришлось добавлять задним числом. У нас по-другому:

- у каждой команды свой struct параметров: `#[derive(Deserialize, JsonSchema)]` и `#[serde(deny_unknown_fields, rename_all = "camelCase")]`;
- JSON Schema параметров генерирует `schemars`; та же схема идёт в MCP (`inputSchema`), в документацию и в UI-формы;
- результат команды — тоже сериализуемый тип, а не собранный вручную JSON.

### 3. UI тонкий и data-driven

- **В `ui-egui` нет бизнес-логики.** Экран рисует состояние и вызывает команды. Если хочется что-то посчитать в UI, это query в engine или функция в `domain`.
- **UI-состояние — простые данные с `serde`** (`state.rs`). Automation может его читать и менять (`ui.inspect` / `ui.set`), а eframe — сохранять между запусками.
- **Цвета, радиусы и отступы берутся только из `theme::Tokens`.** В виджетах их не хардкодим. Общие виджеты лежат в `widgets.rs`; экран не изобретает собственную кнопку.
- **Ошибки команд видны пользователю** (статус-бар или тост). Их не глотают и не превращают в панику.
- **Сеть, диск и всё долгое никогда не выполняются на UI-потоке.** Работа уходит в фоновую задачу, которая вызывает `ctx.request_repaint()`; результат применяется на UI-потоке в `App::logic()`.
- **Платформенные вещи** (файловые диалоги, буфер обмена, keychain) приложение передаёт в UI как `Services`, поэтому `ui-egui` от платформы не зависит.
- `state.rs`, `theme.rs` и `widgets.rs` появятся вместе с первым настоящим экраном.

### 4. Garmin живёт отдельно

- `gymgar-garmin` говорит на модели Garmin: его DTO повторяют их JSON один к одному. Поля, которые мы не моделируем, сохраняются как есть (`#[serde(flatten)] extra: serde_json::Map<String, Value>`). Благодаря этому обновление тренировки в Garmin ничего не теряет.
- Маппинг domain ⇄ Garmin пишется только в `sync`, и у него есть тесты в обе стороны.
- **Тесты никогда не ходят в настоящий Garmin.** Используются записанные ответы (fixtures) и локальный mock-сервер. Перед коммитом fixtures очищаются от персональных данных: имён, email, id устройств и GPS.
- **Секреты** (логин, пароль, токены) хранятся только в системном keychain. Они никогда не попадают в файлы репозитория, логи, тексты ошибок или ответы MCP.

### 5. Единицы и время

- Вес, длительность, дистанция и повторы — типизированные newtype в `domain` (`Mass` и т. п.), а не голые `f32`. Единица отображения (кг или фунты) — настройка пользователя, а не допущение в коде.
- Время идёт через `chrono`: в хранилище UTC, локальная зона только при отображении. Ручную календарную арифметику не пишем.

### 6. Тесты — это ворота

Каждое изменение приходит с тестами:

- `domain` и `sync`: юнит-тесты и round-trip маппинга;
- `engine`: на каждую команду проверяем поведение, undo/redo и недоступное состояние (`enabled`); **плохие параметры должны давать `Err`, а не панику**;
- `garmin`: разбор fixtures, битые ответы, ошибки сети и авторизации;
- `ui-egui`: `egui_kittest::Harness` (headless, без окна).

Интеграционные тесты крейта линкуются в один бинарь: `tests/it/main.rs` плюс `mod <topic>;` на каждую тему.

### 7. UI проверяем глазами

Визуальное изменение проверяется рендером: снапшот kittest (фичи `wgpu` и `snapshot` у `egui_kittest`) сохраняется в PNG, и этот PNG нужно открыть и посмотреть. Не открывай реальное окно, если можно отрендерить offscreen.

## 3. Как делать фичу (вертикальный срез)

Фича проходит слои снизу вверх, и на каждом шаге есть тесты:

1. **domain**: типы и инварианты (валидация в конструкторах).
2. **store**: схема и миграция, если фича что-то хранит.
3. **garmin + sync**: если фича касается Garmin, DTO пишутся в `garmin`, маппинг — в `sync`.
4. **engine**: команды в отдельном модуле `engine/src/<area>_cmds.rs` с функцией `specs()`; в общий реестр добавляется одна строка `v.extend(<area>_cmds::specs())`.
5. **ui-egui**: экран или панель в `ui-egui/src/<area>_ui.rs` (когда разрастётся — каталог `<area>/`), который вызывает команды по id.
6. **automation**: обычно ничего делать не нужно, MCP видит команду через реестр. Отдельный MCP tool нужен, только если агенту нужен специальный интерфейс.
7. Финальная проверка: `cargo xtask ci`.

## 4. Агенты и MCP

- `automation` построен на `rmcp`. Инструменты генерируются из реестра: `command_list` (id, схемы параметров, доступность и причина недоступности), `command_run`, `command_batch`. Рядом лежат curated-инструменты для частых сценариев. Имена MCP tools пишутся в snake_case, id команд — через точку в camelCase.
- Режимы работают как в photocraft. **Headless** (`gymgar-cli mcp`, stdio) поднимает собственную `Session`. **Bridge** подключается к запущенному приложению по loopback TCP с токеном из файла с правами `0600`; так агент видит то же, что пользователь, и не появляется второй писатель в хранилище.
- Безопасность: команды, которые трогают учётные данные (`garmin.login`), агенту недоступны. Секреты не попадают в ответы. Неизвестные аргументы отклоняются до выполнения команды. Ошибка инструмента возвращается как `isError`, а не роняет сервер.

## 5. Организация кода

- Модуль — одна область или фича. Если файл перерос примерно 800 строк, дроби его. Общие файлы (`lib.rs`, реестр команд, `state.rs`) не раздуваем: правки в них маленькие и точечные.
- Модули оформляем в стиле `foo.rs` + `foo/`, без `mod.rs`.
- Юнит-тесты пишем в `#[cfg(test)] mod tests` внизу файла. Если тестов много, выносим их в соседний `foo_tests.rs`.
- Каждый модуль начинается с `//!`: за что он отвечает и чего делать не должен. Комментарии объясняют **почему**, а не что.
- Ошибки — `thiserror`-enum на крейт (`EngineError`, `GarminError`, …). `anyhow` в библиотеках не используем.
- Зависимости объявляются в `[workspace.dependencies]` корневого `Cargo.toml`, крейты подключают их через `{ workspace = true }`. В каждом крейте стоит `[lints] workspace = true`.
- Код, идентификаторы, комментарии и коммиты пишем на английском. Пользовательские строки в коде тоже на английском; когда появится i18n, они пойдут через `tl!()`.
- Стиль: `cargo fmt` (`rustfmt.toml`: ширина 160, `use_small_heuristics = "Max"`) и `cargo clippy -- -D warnings`. Пиши так же, как написан окружающий код.

## 6. Библиотеки

| Задача | Библиотека |
|---|---|
| UI | `eframe` / `egui` 0.37 (wgpu); `egui_extras` для таблиц и SVG-иконок; `egui_plot` для графиков прогресса |
| UI-тесты | `egui_kittest` |
| Сериализация и схемы | `serde`, `serde_json`, `schemars` |
| Ошибки | `thiserror` |
| Логи | `log` (логгер подключает `apps/gymgar`) |
| Время | `chrono` |
| HTTP и async (Garmin) | `reqwest` + `tokio`, только вне UI-потока |
| MCP | `rmcp` (официальный SDK) |
| Секреты | `keyring` |
| Хранилище | пока не решено, см. `docs/architecture.md` › Открытые решения |

Подключаем библиотеку только тогда, когда она реально нужна. Перед этим проверь, нет ли её уже в дереве (`cargo tree -i <crate>`). Если причина зависимости неочевидна, оставь комментарий в `Cargo.toml`.

## 7. Команды

```sh
cargo run -p gymgar                 # desktop-приложение
cargo test -p <crate>               # тесты одного крейта
cargo xtask layers                  # проверка слоёв
cargo xtask ci                      # fmt --check + clippy -D warnings + test --workspace + layers
```

## 8. Прежде чем сказать «готово»

1. `cargo xtask ci` зелёный.
2. Для изменений UI ты посмотрел на отрендеренный PNG.
3. У новых команд есть тест на плохие параметры (`Err`, а не паника) и на undo.
4. Если изменились правила, структура или принятые решения, обнови этот файл и `docs/architecture.md`.

## 9. Параллельные агенты

- Используй свой target-dir (`CARGO_TARGET_DIR=target/agent-<name>`), чтобы не ждать build lock.
- Меняй только свои файлы. Общие файлы (`engine/src/commands.rs`, `lib.rs`, `ui-egui/src/state.rs`) правь маленькими правками и перечитывай их перед редактированием.
- Новые команды клади в новый модуль `<area>_cmds.rs`, а не в общий файл.
- `Cargo.toml` всегда должен быть валиден: из-за glob `crates/*` один битый манифест ломает сборку всем.

## 10. Git

- Ветка по умолчанию — `main`. Коммиты маленькие и сфокусированные; subject на английском в повелительном наклонении.
- Никогда не коммитим секреты, токены и реальные выгрузки из Garmin с персональными данными.
