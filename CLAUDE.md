# CLAUDE.md: руководство для агентов и контрибьюторов

**Gymgar** — нативное desktop-приложение на Rust для силовых тренировок. В нём создают и редактируют тренировки (упражнения, подходы, программы), которые сразу уходят в Garmin Connect. Там же смотрят выполненные активности из Garmin, собирают статистику, строят графики и отчёты с экспортом в CSV, HTML и PDF. Приложение предоставляет MCP-сервер, чтобы агенты могли делать всё то же, что пользователь делает в UI. Интерфейс на английском и русском.

- **Только Rust.** UI на egui/eframe поверх wgpu. Никаких Tauri, Electron, webview или JS/TS.
- **Имя:** в пользовательском тексте пишем **Gymgar**. Машинные имена в нижнем регистре: крейты `gymgar-*`, бинарь `gymgar`, app id `gymgar`.
- **Откуда подход:** структура и практики взяты из [storytold/photocraft](https://github.com/storytold/photocraft). Что именно взяли, что сделали иначе и какие решения ещё открыты, описано в [`docs/architecture.md`](docs/architecture.md). Прочитай его перед первой задачей.

## 1. Карта воркспейса

```text
crates/
  domain       L0  модель: язык, срок ключа Garmin и статус подключения, активности, подходы (запись часов, правки, добавленные, правило «пустой подход»), упражнения, `Mass` и `Reps`, прогресс по упражнению (`progress`: правило подсказки «держим или добавляем» и ряд графика «вес на N повторов»); дальше тренировки, программы, остальные единицы (чистые данные, без I/O)
  garmin       L0  standalone-клиент Garmin: `personal` — Personal API (обмен ключа на токен, список активностей и файл активности сырыми байтами, один повтор после 401), `fit` — ZIP и `.FIT` силовой тренировки в DTO Garmin, каталог упражнений (писатели FIT и ZIP для тестов — фича `testing`), `connect` — web-API (тренировки; будет)
  secrets      L0  standalone-хранилище секретов: системное (`keyring`: Keychain, Credential Manager, Secret Service) и файловое (запасное, `0600`)
  store        L1  SQLite-хранилище: файл в каталоге данных, WAL, миграции через `PRAGMA user_version`, настройки и подключение Garmin, активности с файлами и подходами из записи, правки и добавленные подходы, история учитываемых подходов для прогресса (`strength_history`), состояние загрузки (дальше тренировки и корзина)
  report       L1  (появится вместе с отчётами) рендеринг отчёта в CSV, HTML и PDF
  sync         L2  Garmin → domain: список активностей и файл силовой в типы `domain`, каталог упражнений и какие из них силовые, правила темпа загрузки; чистые функции, без сети и хранилища (двусторонний синк тренировок и конфликты появятся позже)
  engine       L3  Session + реестр команд (каждое действие — команда; `progress.list` и `progress.get` собирают прогресс из истории), фоновые задачи с промежуточными результатами; сервисы снаружи (`SecretStore`, `GarminAuth` и `GarminSession`, `Spawner`) — трейтами
  ui-egui      L4  egui-оболочка (тонкая: все действия идут через engine): тема «Спорт», i18n en/ru, полоса иконок, экраны «Сводка», «Тренировки», «Прогресс» и «Настройки»
  automation   L4  MCP-сервер (rmcp) поверх реестра команд: `command_list`, `command_run`
apps/
  gymgar           desktop-приложение (eframe): окно, свой небольшой логгер, адаптеры (keychain, файл, Garmin, tokio runtime), сборка всего вместе
  gymgar-cli       headless CLI: `gymgar-cli mcp` (stdio); в Garmin он не ходит (загрузку делает приложение), экспорт отчётов появится позже
fixtures/garmin/   очищенные ответы Garmin для тестов (файл силовой, страница списка); только результат `cargo xtask scrub-*`, см. README в каталоге
xtask/             cargo xtask ci | layers | scrub-fit | scrub-list
```

**Слои проверяет `cargo xtask layers`** (`xtask/src/layers.rs` читает `cargo metadata`):

- крейт зависит только от крейтов **более низкого** слоя: без циклов и без зависимостей «вбок»;
- standalone-крейт (`garmin`, `secrets`) не зависит ни от одного крейта воркспейса, поэтому маппинг живёт в `sync`, а выбор хранилища и трейты для него — в `engine` и в приложениях;
- `engine` напрямую не зависит ни от `garmin`, ни от `secrets`. Он зависит от `sync` (L3 → L2), поэтому `garmin` попадает в его дерево транзитивно, но сам `engine` не называет ни одного типа `garmin` (в `[dev-dependencies]` есть только `garmin` с фичей `testing`: писатели FIT и ZIP для тестов). Он объявляет трейты (`SecretStore`, `GarminAuth` и `GarminSession`, `Spawner`): сеть отдаёт сырые байты, а разбор и маппинг делает `sync`. Адаптеры к трейтам лежат в `apps/gymgar/src/services.rs`. Так команды тестируются с подставными реализациями, без сети и без настоящего хранилища (`engine::testing`, фича `testing`);
- UI-тулкит (egui, eframe, winit, wgpu, rfd, egui_extras, egui_plot) разрешён только в `ui-egui` и `apps/*`;
- новый крейт регистрируется в `TABLE` в `xtask/src/layers.rs` под именем без префикса `gymgar-` (пакет `gymgar-cli` — это `cli`), иначе проверка падает. Сейчас в воркспейсе 11 крейтов: 8 библиотек, 2 приложения и `xtask`.

`sync` пока отвечает только за загрузку активностей. Двусторонний синк тренировок и конфликты наполнят его по мере появления фич.

## 2. Золотые правила

### Never crash (важнее любой фичи)

Пользователь доверяет приложению свои тренировки, и паника означает потерянные данные. Битый ответ Garmin, неверные MCP-параметры, испорченный файл, пропавшая сеть или полный диск должны давать понятную ошибку, а не панику.

- **Не-тестовый код не паникует.** Запрещены `unwrap`, `expect`, `panic!`, `unreachable!`, `todo!`, `unimplemented!` и индексация `[i]`. Возвращай ошибку крейта и пробрасывай её через `?`. Используй `ok_or(..)?`, `let .. else`, `get()`. `unwrap_or*` допустим только там, где fallback действительно корректен; fallback, который тихо портит данные, недопустим. Незавершённая функциональность возвращает ошибку «unsupported». Единственное исключение — доказуемо безошибочный литерал: `#[allow(clippy::expect_used)]` плюс `.expect("почему это не упадёт")`.
- **Это проверяется автоматически:** `[workspace.lints.clippy]` в `Cargo.toml` ставит `deny`, а `clippy.toml` ослабляет правила только внутри тестов.
- **`unsafe` запрещён** (`unsafe_code = "forbid"`).
- **Внешние данные враждебны** (Garmin, MCP, файлы, ввод в UI). Для длин и счётчиков используй `checked_*` и `saturating_*`. Защищайся от деления на ноль и от NaN/inf. Ограничивай аллокации, размер которых пришёл извне. Строки режь только по границам символов.
- **Не допускай каскадов.** При отравлении мьютекса используй `lock().unwrap_or_else(PoisonError::into_inner)`. `join()` потока возвращает `Result`, обрабатывай его.
- **Последний рубеж.** Паника не роняет приложение, а становится ошибкой: в `Session::execute` и при применении результата задачи в `Session::poll_jobs` — `EngineError::CommandPanicked` (только id команды, без параметров), внутри фоновой задачи — `EngineError::JobPanicked`, в обработчике MCP — ошибкой инструмента. `panic = "unwind"` не меняем. Это страховка, а не разрешение паниковать. Каких защит ещё нет (panic hook, который пишет в лог) — в `docs/architecture.md` › «Известные пробелы».
- **Докажи фикс.** Каждое исправление краша идёт вместе с регрессионным тестом, который падал до исправления.

### 1. Всё — команда

Любое пользовательское действие — это команда в `engine` со стабильным id вида `area.action` в camelCase: `workout.create`, `workout.addExercise`, `exercise.rename`, `garmin.sync`, `stats.volumeByWeek`. UI, CLI и MCP вызывают **одну и ту же** точку входа `Session::execute(id, params)`. Только чисто визуальное состояние (выбранная вкладка, ширина панели, прокрутка) живёт в UI, а не в engine.

Команда описывается `CommandSpec`: `id`, `label`, путь в меню, хоткей, **типизированные параметры**, `enabled` (с причиной, почему команда сейчас недоступна), `run`, вид (query, мутация или фоновая задача), флаг «можно ли вызывать агенту» и флаг «разрушительная».

**Undo нет** (`docs/architecture.md` › решение 5). Поэтому мутация выполняется **одной транзакцией SQLite**: если на середине возникла ошибка, не меняется ничего. Разрушительные команды UI подтверждает у пользователя, а MCP помечает как `destructive`. Механизм истории не пишем, пока его не попросят.

**Удаление — в корзину** (решение 10). Удалённая запись получает `deleted_at`, пропадает из списков и статистики и восстанавливается командой. Каждый запрос к хранилищу явно учитывает корзину: по умолчанию удалённые записи не возвращаются. Очистка корзины удаляет навсегда, требует подтверждения в UI и агенту недоступна.

### 2. Параметры команд типизированы (здесь мы отличаемся от photocraft)

У photocraft параметры — свободный `serde_json::Value` плюс строка-описание, и проверку опечаток в ключах им пришлось добавлять задним числом. У нас по-другому:

- у каждой команды свой struct параметров: `#[derive(Deserialize, JsonSchema)]` и `#[serde(deny_unknown_fields, rename_all = "camelCase")]`;
- JSON Schema параметров генерирует `schemars`; та же схема идёт в MCP (`inputSchema`), в документацию и в UI-формы;
- результат команды — тоже сериализуемый тип, а не собранный вручную JSON.

### 3. UI тонкий и data-driven

- **В `ui-egui` нет бизнес-логики.** Экран рисует состояние и вызывает команды. Если хочется что-то посчитать в UI, это query в engine или функция в `domain`.
- **UI-состояние — простые данные с `serde`** (`state.rs`). eframe сохраняет его между запусками; automation сможет читать и менять его (`ui.inspect` / `ui.set`) вместе с bridge-режимом. Всё, что принадлежит engine (язык, подключение Garmin), UI не копирует, а читает командой. Сохраняются раздел, срок ключа, фильтр с выбранной активностью на экране «Тренировки» и фильтр с открытым упражнением на экране «Прогресс». Состояние минуты (введённый ключ, ошибка, идущая проверка или отключение, согласие, подтверждение, строка правки подхода, открытый поиск упражнения) не сохраняется: ключ вообще не сериализуется.
- **Цвета, радиусы и отступы берутся только из `theme::Tokens`.** В виджетах их не хардкодим. Общие виджеты лежат в `widgets.rs`; экран не изобретает собственную кнопку.
- **Интерфейс двуязычный: английский и русский.** Каждая строка, которую видит пользователь, оборачивается в `tl!("English text")`. Исходный текст — сам английский литерал. Русские строки лежат в `crates/ui-egui/i18n/ru.tsv` (пара `English<TAB>Русский` на строку). Для чисел есть `i18n::trn(n, one, few, many)`: у русского три формы («1 подход», «3 подхода», «5 подходов»). Язык выбирается в настройках: системный, English или Русский; `settings.setLanguage` меняет его на лету. Названия языков в списке — самоназвания («English», «Русский»): они одинаковы на любом языке интерфейса, поэтому в `tl!` не оборачиваются. Тест падает, если у литерала `tl!` нет перевода в `ru`. Если один английский текст по-русски говорится по-разному, к литералу дописывают контекст: `tl!("May|label")`. Английский показывает текст до `|`, а ключ в каталоге `ru` — весь литерал целиком (`May|label<TAB>май`: подпись месяца на оси графика в именительном падеже, а в датах `May` — «мая»). Id команд, параметры, MCP и логи остаются на английском.
- **В тексте интерфейса только символы из шрифтов egui, которые идут в комплекте.** Иначе на минимальном Linux будут «тофу», а проверка отсутствующих глифов в тестах UI падает: стрелки рисуем `painter`'ом (так сделан шеврон «можно добавлять»).
- **Ошибки команд видны пользователю**: в баннере вверху экрана (он остаётся, пока следующее действие пользователя не пройдёт успешно) или рядом с формой либо строкой, которую пользователь правит. Их не глотают и не превращают в панику. Сбой записи части того, что прислала фоновая задача, показывается один раз за задачу. Engine формулирует ошибки по-английски, потому что их читают и агенты; UI показывает пользователю переведённый текст, определяя его по варианту enum-ошибки.
- **Сеть, диск и всё долгое никогда не выполняются на UI-потоке.** Работа уходит в фоновую задачу, которая вызывает `ctx.request_repaint()`; результат применяется на UI-потоке в `App::logic()` через `Session::poll_jobs`.
  - Задача может присылать промежуточные результаты (`JobCtx::send`: так `garmin.sync` отдаёт каждую страницу списка и каждый файл). Их применяют по одному, в порядке отправки, каждый в своей транзакции; за один вызов применяется ограниченное число, остальное досыпается в следующем кадре.
  - Задача получает снимок данных на старте, в базу не заглядывает и не пишет в неё: в базу пишет только `poll_jobs` на потоке сессии. Обращения к хранилищу секретов (чтение ключа, сохранение принятого Garmin ключа, удаление) делает сама задача, чтобы системный запрос доступа не заморозил окно. Откат ключа при сбое записи и удаление заменённого ключа уходят на spawner без ожидания (`spawn_tail`), сбой только логируется.
  - Паузы между запросами идут через внедрённый `Services.sleep`, поэтому тесты не ждут. Паника задачи — `EngineError::JobPanicked`; задача, которую spawner бросил, заканчивается `EngineError::JobDropped` и не числится выполняющейся вечно.
  - Пока идёт синк, команды ключа (`garmin.connect`, `garmin.verify`, `garmin.disconnect`) недоступны, а `garmin.sync` и `activity.reparse` не работают одновременно.
- **Платформенные вещи** (keychain, сеть, async runtime, часы) приложение передаёт в engine как `Services`, поэтому ни `engine`, ни `ui-egui` от платформы не зависят. Файловые диалоги и буфер обмена придут тем же путём, когда понадобятся.
- Каркас UI лежит в `crates/ui-egui/src`: `state.rs` (состояние), `theme.rs` (токены `Tokens::SPORT`), `widgets.rs` (общие виджеты, в том числе `sparkline` плитки прогресса), `i18n.rs` (`tl!`, `trn`), `rail.rs` (полоса иконок), `dates.rs` и `numbers.rs` (даты, числа, вес и длительности по правилам языка), экраны `summary_ui.rs`, `activities_ui.rs` (список активностей), `activity_detail_ui.rs` (открытая активность), `set_edit_ui.rs` (правка подходов, выбор упражнения, добавление подхода), `progress_ui.rs` (плитки упражнений с подсказкой), `progress_detail_ui.rs` (одно упражнение: карточка подсказки, график, занятия), `progress_chart.rs` (график «вес на N повторов» на `egui_plot`) и `settings_ui.rs`. Новый экран берёт цвета и виджеты оттуда.

### 4. Garmin живёт отдельно

Каналов два, подробности в `docs/architecture.md` › §6.

- **Чтение — официальный Personal API** (модуль `garmin::personal`). Пользователь сам выпускает личный ключ на странице [Personal API Key](https://connect.garmin.com/app/settings/personalApiToken) в Garmin Connect и вставляет его в Gymgar. Приложение обменивает ключ на access token (живёт 24 часа, refresh-токена нет) и при необходимости получает новый тем же запросом. Срок действия ключа — от 30 дней до года, но ни в ключе, ни в токене его нет: пользователь указывает срок при подключении, а Gymgar предупреждает за 7 дней до конца. Когда Garmin отвечает 401 (ключ истёк, удалён или срок выбран неверно), UI объясняет, где выпустить новый, и ничего не удаляет сам. API только читает: активности (JSON и `.FIT`) и данные о здоровье. Загрузку активностей ведёт задача `garmin.sync`: при старте приложения (после `activity.reparse`, если файлы пора разобрать заново), при подключении ключа в окне и по кнопке «Обновить», но не по таймеру. В каждый момент идёт один запрос; между файлами пауза 2 с, на 429, 5xx и ошибки сети — повторы с паузами 30, 120 и 300 с, потом остановка (константы в `sync::policy`). Файл скачивается только у силовой активности (`activityType.typeKey == "strength_training"`). 401 клиент `garmin::personal` обрабатывает сам: один новый токен и один повтор запроса, второй 401 — ключ не действует.
- **Запись тренировок — недокументированное web-API Garmin Connect** (модуль `garmin::connect`), и только для редких необходимых действий: создать, изменить или удалить тренировку и прочитать её текущую версию перед изменением. Фонового опроса нет. Всё, что умеет Personal API, читается только через него. Web-API хрупкое: в 2026 году Garmin уже менял авторизацию, на частые входы отвечает 429. Поэтому:
  - вход по логину, паролю и коду MFA выполняется только по действию пользователя в UI; пароль нигде не хранится, остаются только токены; автоматического повторного входа нет;
  - у `garmin::connect` свои ошибки, и его поломка не задевает `garmin::personal`: статистика и отчёты продолжают работать, тренировки ждут в Gymgar;
  - поток входа и форматы снимаются с живого аккаунта и хранятся как очищенные fixtures.
- **Тренировки синхронизируются в обе стороны**, по действию пользователя, а не по таймеру. Для каждой храним базовую версию с последнего синка. Если тренировку изменили и в Gymgar, и в Garmin, это конфликт: пользователь разрешает его вручную на отдельном экране. Автоматически ничего не перезаписываем.
- **Корзина и Garmin.** Перенос тренировки в корзину сразу удаляет её из Garmin, восстановление загружает её заново. Если Garmin недоступен, операция ждёт в очереди синка.
- `gymgar-garmin` говорит на модели Garmin: его DTO повторяют их JSON один к одному и не теряют неизвестные поля (`#[serde(flatten)] extra: serde_json::Map<String, Value>`). Сырые ответы (JSON и `.FIT`) сохраняются в базе, чтобы новую статистику можно было посчитать без повторной загрузки.
- Маппинг Garmin → domain пишется только в `sync` и покрыт тестами.
- **Правки пользователя живут отдельно от записи часов.** Подход из записи определяется парой `(activityId, message_index)` сообщения `set` и является производной от файла: `recorded_set` можно стереть и собрать заново (`activity.reparse`). Правки (`set_correction`, `added_set`) повторная загрузка и повторный разбор не трогают, в Garmin они не уходят. Подход, которого после разбора в файле нет, остаётся в базе и просто не показывается. Пустой подход (нет повторов или 0, нет веса или 0, короче 10 с) автоматически не учитывается, разминка и кардио учитываются; выбор пользователя («учитывать» или нет) сильнее этого правила (а исключённая целиком активность сильнее всего), добавленные пользователем подходы ему не подчиняются.
- **Тесты никогда не ходят в настоящий Garmin.** Используются записанные ответы (fixtures) и локальный mock-сервер. Fixtures попадают в репозиторий только через `cargo xtask scrub-fit` (файл активности) и `cargo xtask scrub-list` (страница списка): они не замазывают настоящий ответ, а строят выход заново из того, что читает приложение, поэтому имён, email, id устройств, серийных номеров и GPS в нём нет. Руками fixtures не правим, настоящие выгрузки остаются вне репозитория; порядок работы и проверка перед коммитом — в `fixtures/garmin/README.md`.
- **Секреты.** Ключ Personal API хранится в системном хранилище секретов (Keychain, Credential Manager, Secret Service; service `gymgar`, account `garmin-personal-api-key`), токены web-API — там же. Access token Personal API живёт только в памяти, пароль не хранится нигде. Секреты не попадают в файлы репозитория, базу, логи, тексты ошибок или ответы MCP.
  - **Секрет — только `secrecy::SecretString`.** Он не печатается в `Debug` и `Display` и затирается при сбросе. В параметрах команд такое поле помечается `#[schemars(with = "String")]`: serde десериализует его (`secrecy` с фичей `serde`), а сериализовать его нельзя; в JSON Schema он выглядит обычной строкой. В аргументы командной строки процесса секрет тоже не попадает. В логах пишем id команды, но не параметры.
  - **Запасное файловое хранилище.** Если системного хранилища нет (минимальный Linux), ключ можно сохранить в файл `<каталог данных>/secrets/garmin-personal-api-key` с правами `0600`, но только с явного согласия пользователя в UI, и предупреждение называет путь к файлу. Выбранное хранилище записывается в `garmin_connection.secret_backend`, и проверка читает ключ оттуда же. Автоматического перехода между хранилищами нет, и сбой системного хранилища не превращается молча в запись в файл. Если новое подключение сохранило ключ в другое хранилище, ключ прежнего подключения удаляется оттуда (по возможности и в фоне: сбой только логируется). Ключ при подключении сохраняет сама задача `garmin.connect`, а не поток сессии; `garmin.disconnect` — тоже задача (разрушительная и закрытая агенту). В общей базе SQLite ключа не бывает никогда.
  - **Отладочные сборки не трогают системное хранилище** (даже не проверяют его): ключ идёт в файл, а каталог данных называется `Gymgar Dev` (macOS и Windows) или `gymgar-dev` (Linux), в релизной сборке — `Gymgar` или `gymgar`. Так macOS не просит доступ к Keychain после каждой пересборки, а сборка разработчика не делит базу и ключ с настоящей установкой. Релизная сборка проверяет системное хранилище один раз при старте, на отдельном потоке и до создания окна: запрос системы на доступ не должен замораживать окно. Чтобы проверить путь через Keychain, запускай `cargo run --release -p gymgar`.
  - **Не вводи ключ в терминале macOS через `security` с интерактивным запросом:** ввод пароля там (`getpass`) обрезает строку до 128 символов, а настоящий ключ — 132, и Garmin отвечает 401. Поле в приложении и хранилища принимают ключ любой длины; «ключ обрезался» — анти-цель.

### 5. Отчёты

- Отчёт — модель данных (разделы, таблицы, ряды графиков), которую строит query в engine. Рендереры только рисуют её и сами ничего не считают: в приложении — `egui_plot`, при экспорте — крейт `report` (CSV, HTML, PDF).
- График описывается одной спецификацией (данные, оси, серии, цвета из темы), поэтому в приложении и в файле он выглядит одинаково. Общая спецификация появится вместе с проектом отчётов, когда у графика будет второй рендерер; пока рендерер один (`egui_plot`), и моделью графика служат сериализуемые ответы `progress.list` и `progress.get` (решение 9, уточнение проекта 3 в `docs/architecture.md`).
- HTML-файл самодостаточный: стили и SVG-графики лежат внутри, внешних скриптов и ссылок нет. PDF рисует те же SVG-графики.
- Экспорт через MCP пишет файлы только в каталог, который пользователь разрешил заранее.

### 6. Единицы и время

- Вес, длительность, дистанция и повторы — типизированные newtype в `domain` (`Mass` и т. п.), а не голые `f32`. Единица отображения (кг или фунты) — настройка пользователя, а не допущение в коде.
- Время идёт через `chrono`: в хранилище UTC, локальная зона только при отображении. Единственное исключение — день и месяц занятия в прогрессе: они берутся из местного времени начала, которое отдаёт Garmin (`startTimeLocal`), а запасной вариант — UTC. Ручную календарную арифметику не пишем.

### 7. Тесты — это ворота

Каждое изменение приходит с тестами:

- `domain` и `sync`: юнит-тесты; для `sync` — маппинг на записанных ответах Garmin;
- `store`: миграции на временной базе; база, созданная предыдущей версией схемы, открывается и мигрирует без потерь; удалённое в корзину не попадает в обычные выборки и восстанавливается;
- `report`: CSV сравнивается с эталоном байт в байт; HTML — снапшотом; PDF открывается и содержит нужные страницы;
- `engine`: на каждую команду проверяем поведение, атомарность (ошибка на середине ничего не меняет) и недоступное состояние (`enabled`); **плохие параметры должны давать `Err`, а не панику**;
- `garmin`: разбор fixtures, битые ответы, ошибки сети и авторизации (истёкший ключ, 429, MFA);
- `sync`: конфликт тренировки (изменена с обеих сторон) обнаруживается и ничего не перезаписывает;
- `ui-egui`: `egui_kittest::Harness` (headless, без окна).

Интеграционные тесты крейта линкуются в один бинарь: `tests/it/main.rs` плюс `mod <topic>;` на каждую тему.

### 8. UI проверяем глазами

Визуальное изменение проверяется рендером: снапшот kittest (фичи `wgpu` и `snapshot` у `egui_kittest`) сохраняется в PNG, и этот PNG нужно открыть и посмотреть. Не открывай реальное окно, если можно отрендерить offscreen.

## 3. Как делать фичу (вертикальный срез)

Фича проходит слои снизу вверх, и на каждом шаге есть тесты:

1. **domain**: типы и инварианты (валидация в конструкторах).
2. **store**: таблицы и миграция SQLite, если фича что-то хранит.
3. **garmin + sync**: если фича касается Garmin, DTO пишутся в `garmin`, маппинг — в `sync`.
4. **engine**: команды в отдельном модуле `engine/src/<area>_cmds.rs` с функцией `specs()`; в общий реестр добавляется одна строка `v.extend(<area>_cmds::specs())`.
5. **ui-egui**: экран или панель в `ui-egui/src/<area>_ui.rs` (когда разрастётся — каталог `<area>/`), который вызывает команды по id. Новые строки сразу переводятся в каталоге `ru`.
6. **automation**: обычно ничего делать не нужно, MCP видит команду через реестр. Отдельный MCP tool нужен, только если агенту нужен специальный интерфейс.
7. Финальная проверка: `cargo xtask ci`.

## 4. Агенты и MCP

- `automation` построен на `rmcp`. Инструменты генерируются из реестра: `command_list` (id, схемы параметров, доступность и причина недоступности) и `command_run`; `command_batch` и curated-инструменты для частых сценариев добавим позже. Имена MCP tools пишутся в snake_case, id команд — через точку в camelCase.
- Режимы работают как в photocraft. **Headless** (`gymgar-cli mcp`, stdio) поднимает собственную `Session` на той же базе; пока есть только он. **Bridge** отложен до проекта, где он понадобится: он подключится к запущенному приложению по loopback TCP с токеном из файла с правами `0600`, и агент сможет запускать загрузку и проверку ключа в открытом приложении. Сейчас массовую запись (загрузку активностей) делает только приложение, а CLI пишет коротко: язык, правки подходов, исключение активности. Поэтому до bridge приложение и `gymgar-cli` пишут в базу параллельно (WAL, `busy_timeout` 5 с, короткие транзакции), а окно раз в секунду сверяет `PRAGMA data_version`: язык или правка подхода, сделанные агентом, применяются на лету.
- `gymgar-cli` не получает ни хранилища секретов, ни клиента Garmin, ни spawner'а (`Services` с `None`): что бы ни делал агент, процесс не откроет keychain и не пойдёт в сеть.
- Безопасность: команда с флагом `agent: false` не видна в `command_list`, а `command_run` для неё отказывает (проверка в `Session::execute`). Сейчас агенту доступны `garmin.status`, `settings.get`, `settings.setLanguage`, `activity.list`, `activity.get`, `activity.setExcluded`, `activity.editSets`, `activity.resetSets`, `activity.addSet`, `activity.removeAddedSet`, `exercise.search`, `progress.list` и `progress.get` (две последние только читают: упражнения с подсказкой «держим или добавляем» и одно упражнение целиком, с рядом графика, занятиями и основанием подсказки; агент видит то же, что плитки на экране «Прогресс»). Скрыты ввод ключа (`garmin.connect`), проверка ключа (`garmin.verify`: она читает ключ, а для отдельного бинаря `gymgar-cli` это системный диалог доступа к связке ключей; станет доступна с bridge, когда ключ будет читать приложение), `garmin.disconnect`, загрузка из Garmin (`garmin.sync`), повторный разбор файлов (`activity.reparse`) и `activity.markSeen`: пометка «новая» нужна глазам пользователя, поэтому её снимает только открытие активности в окне, а чтение (`activity.get`) её не снимает. Правки подходов агент делает теми же командами, что и UI; запись часов они не стирают, и правку подхода из записи можно вернуть (`activity.resetSets`). Ответы `activity.list`, `activity.get` и `progress.*` не содержат сырого JSON Garmin, файлов и личных полей (`owner*`). Позже так же скроются вход в Garmin (`garmin.login`) и очистка корзины (`trash.empty`). Удалять агент сможет только в корзину. Разрушительные команды помечены `destructiveHint`; сейчас такая одна, `garmin.disconnect`, и она закрыта агенту. Команды активностей не стирают запись часов: `activity.resetSets` удаляет правки пользователя (подход снова такой, каким его записали часы), а `activity.removeAddedSet` переносит добавленный подход в корзину (`deleted_at`). Экспорт будет писать файлы только в разрешённый каталог. Секреты не попадают в ответы. Неизвестные аргументы отклоняются до выполнения команды. Ошибка инструмента возвращается как `isError`, а не роняет сервер.

## 5. Организация кода

- Модуль — одна область или фича. Если файл перерос примерно 800 строк, дроби его. Общие файлы (`lib.rs`, реестр команд, `state.rs`) не раздуваем: правки в них маленькие и точечные.
- Модули оформляем в стиле `foo.rs` + `foo/`, без `mod.rs`.
- Юнит-тесты пишем в `#[cfg(test)] mod tests` внизу файла. Если тестов много, выносим их в соседний `foo_tests.rs`.
- Каждый модуль начинается с `//!`: за что он отвечает и чего делать не должен. Комментарии объясняют **почему**, а не что.
- Ошибки — `thiserror`-enum на крейт (`EngineError`, `GarminError`, …). `anyhow` в библиотеках не используем.
- Зависимости объявляются в `[workspace.dependencies]` корневого `Cargo.toml`, крейты подключают их через `{ workspace = true }`. В каждом крейте стоят `[lints] workspace = true` и `license.workspace = true`.
- Код, идентификаторы, комментарии и коммиты пишем на английском. Пользовательские строки в коде тоже на английском и всегда внутри `tl!()`; русский перевод лежит в каталоге `ru`.
- Стиль: `cargo fmt` (`rustfmt.toml`: ширина 160, `use_small_heuristics = "Max"`) и `cargo clippy -- -D warnings`. Пиши так же, как написан окружающий код.

## 6. Библиотеки

| Задача | Библиотека |
|---|---|
| UI | `eframe` / `egui` 0.37 (wgpu); `egui_extras` для таблиц и SVG-иконок; `egui_plot` 0.38 для графика прогресса (подключён в `ui-egui`: `progress_chart.rs`) |
| UI-тесты | `egui_kittest` |
| Сериализация и схемы | `serde`, `serde_json`, `schemars` |
| Ошибки | `thiserror` |
| Логи | `log`; логгер свой и небольшой (`apps/gymgar/src/logging.rs`): умолчанию нужны фильтр по семейству `gymgar*` (`info` для наших крейтов, `warn` для остальных, `RUST_LOG` переопределяет) и вывод в stderr и в файл `logs/gymgar.log` одновременно. Если логам понадобится больше (ротация по размеру, структурные поля), заменить готовым крейтом |
| Время | `chrono` |
| HTTP и async (Garmin) | `reqwest` + `tokio`, только вне UI-потока |
| Разбор `.FIT` (активности) | `fitparser` — кандидат, проверить перед подключением |
| Экспорт отчётов | CSV — `csv`; графики в файлах — SVG; PDF — `krilla` + `svg2pdf` (кандидаты, чистый Rust; проверить перед подключением) |
| MCP | `rmcp` (официальный SDK) |
| Секреты | `keyring` 4 (системное хранилище: Keychain, Credential Manager, Secret Service через чистый Rust, без `libdbus`) |
| Секреты в памяти | `secrecy` (`SecretString`: не печатается, затирается при сбросе; фича `serde` — только десериализация) |
| Хранилище | `rusqlite` с фичей `bundled` (SQLite собирается вместе с приложением), режим WAL, миграции через `PRAGMA user_version` |
| Локализация | своя: макрос `tl!()` и каталог `ru` в `crates/ui-egui/i18n/ru.tsv`; `sys-locale` определяет системный язык |
| Каталоги данных | `directories` (`ProjectDirs::from_path` с точными именами `Gymgar` / `Gymgar Dev`, на Linux `gymgar` / `gymgar-dev`) |
| JSON Schema команд | `schemars` (одна схема для MCP, документации и форм) |

Подключаем библиотеку только тогда, когда она реально нужна. Перед этим проверь, нет ли её уже в дереве (`cargo tree -i <crate>`). Если причина зависимости неочевидна, оставь комментарий в `Cargo.toml`.

## 7. Команды

```sh
cargo run -p gymgar                 # desktop-приложение, отладочная сборка (каталог `Gymgar Dev`, ключ в файле)
cargo run --release -p gymgar       # релизная сборка: настоящий каталог данных, ключ в системном хранилище
cargo run -p gymgar-cli -- mcp      # headless MCP-сервер по stdio
cargo test -p <crate>               # тесты одного крейта
cargo xtask layers                  # проверка слоёв
cargo xtask ci                      # fmt --check + clippy -D warnings + test --workspace + layers
```

**CI** (`.github/workflows/ci.yml`) на каждый push и pull request гоняет `cargo xtask ci` на `ubuntu-latest`, `windows-latest` и `macos-latest`. Код должен собираться и проходить тесты на всех трёх ОС, поэтому: пути собираем через `Path`, платформенный код закрываем `#[cfg]` с вариантом для остальных ОС, в тестах не полагаемся на настоящее системное хранилище и сеть (тест настоящего хранилища помечен `#[ignore]` и использует фиктивный секрет). На Linux workflow ставит системные пакеты для egui и winit; если новая зависимость просит ещё один, добавь его туда.

## 8. Прежде чем сказать «готово»

1. `cargo xtask ci` зелёный локально, и CI зелёный на всех трёх ОС.
2. Для изменений UI ты посмотрел на отрендеренный PNG.
3. У новых команд есть тест на плохие параметры (`Err`, а не паника) и на атомарность.
4. Новые строки UI переведены в каталоге `ru`.
5. Если изменились правила, структура или принятые решения, обнови этот файл и `docs/architecture.md`.

## 9. Параллельные агенты

- Используй свой target-dir (`CARGO_TARGET_DIR=target/agent-<name>`), чтобы не ждать build lock.
- Меняй только свои файлы. Общие файлы (`engine/src/commands.rs`, `lib.rs`, `ui-egui/src/state.rs`) правь маленькими правками и перечитывай их перед редактированием.
- Новые команды клади в новый модуль `<area>_cmds.rs`, а не в общий файл.
- `Cargo.toml` всегда должен быть валиден: из-за glob `crates/*` один битый манифест ломает сборку всем.
