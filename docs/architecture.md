# Архитектура Gymgar

> **Обновлено:** 2026-10-23 · **Источник подхода:** [storytold/photocraft](https://github.com/storytold/photocraft) (изучена ветка `main` на 2026-10-23)

Короткие правила для ежедневной работы лежат в [`CLAUDE.md`](../CLAUDE.md). Здесь объясняется, откуда они взялись, как устроено приложение во время работы и какие решения ещё не приняты.

## 1. Почему photocraft

PhotoCraft — open-source клон Photoshop, написанный только на Rust: 25 библиотечных крейтов, около 540 тыс. строк и около 8 тыс. тестов. UI сделан на egui/eframe поверх wgpu. В движке зарегистрировано около 700 команд, и все фронтенды — GUI, headless CLI, JSON control channel и MCP-сервер — вызывают их по id. Форма та же, что нужна нам: desktop-редактор, которым агент может управлять так же полно, как человек. Масштаб у нас на порядки меньше, поэтому из photocraft мы берём принципы, а не весь его аппарат.

## 3. Что делаем иначе и почему

- **Типизированные параметры команд.** В собственном плане photocraft (§4.2) параметры описывались схемой `schemars`, но реализованы как `&serde_json::Value` плюс строка-описание. Опечатка в ключе тихо запускала команду со значениями по умолчанию, и проверку пришлось добавлять задним числом (`param_check.rs`, список `STRICT`). У нас каждая команда сразу получает struct с `deny_unknown_fields` и схемой `schemars`.
- **Lints на весь воркспейс с первого дня.** У photocraft `#![deny(...)]` стоит в каждом крейте отдельно, потому что часть старого кода ещё не вычищена. Нам наследство не мешает, поэтому правила лежат в `[workspace.lints.clippy]`, включая `indexing_slicing`.
- **Нет wasm и веб-сборки.** Синк с Garmin, keychain и MCP — нативные вещи, поэтому wasm-гейт нам не нужен. `domain` и `engine` всё равно держим без платформенных зависимостей.
- **Файлы меньше.** В `ui-egui/src` у photocraft 375 файлов в одной папке и `lib.rs` на тысячи строк. Мы группируем область в каталог, как только у неё больше трёх-четырёх файлов, и дробим файлы примерно от 800 строк.
- **Крейтов меньше.** Семь вместо 25; делим, когда крейт разрастается или начинает мешать время компиляции.
- **Не берём механику паритета с Photoshop** (`menu_catalog`, `parity`, `scorecard`, corpus): нам она не нужна.
- **Нет undo** (решение 5). В редакторе изображений история шагов обязательна, а у нас правки мелкие и структурные. Каждая мутирующая команда — одна транзакция SQLite: она применяется целиком или не применяется вовсе. Разрушительные команды подтверждаются в UI и помечаются для MCP как destructive. Все правки идут через `execute`, поэтому историю можно добавить позже, не переписывая команды.

## 4. Слои

```text
 L5  apps/gymgar · apps/gymgar-cli        бинари: собирают всё вместе (без ограничений)
 L4  ui-egui · automation                 фронтенды движка (UI-тулкит — только в ui-egui)
 L3  engine                               Session, реестр команд, задачи
 L2  sync                                 активности из Garmin, двусторонний синк тренировок, конфликты
 L1  store · report                       SQLite-хранилище; экспорт отчётов в CSV/HTML/PDF (report появится вместе с отчётами)
 L0  domain                               garmin (standalone, без зависимостей от воркспейса)
```

## 5. Модель выполнения

```text
 UI-поток (egui) ──execute(id, params)──► Session (владеет моделью и реестром команд)
     ▲   App::logic(): опрос задач, запросы bridge, применение результатов
     │
     └──── результаты и прогресс ◄──── фоновые задачи (воркеры / tokio runtime):
                                        синк с Garmin, импорт, экспорт
```

- `Session` живёт на UI-потоке и выполняет команды синхронно, как в photocraft. Всё долгое уходит в задачу: она получает копию нужных данных, флаг отмены и канал прогресса, а результат применяется через тот же путь, что и `execute`.
- Сетевой код асинхронный (`reqwest` + `tokio`). Runtime принадлежит приложению; на UI-потоке `block_on` не вызываем. Задача сама будит UI через `ctx.request_repaint()`.
- Хранилище — одна база SQLite (решение 1) в каталоге данных приложения, в режиме WAL. Мутирующая команда — одна транзакция. Состояние синка (id активностей в Garmin, время последней загрузки) лежит в той же базе.

## 6. Garmin Connect

С Garmin работаем по двум каналам (решение 12). Активности и данные о здоровье читаем через официальный Personal API (§6.1). Недокументированное web-API Garmin Connect (§6.2) вызываем только для редких необходимых действий с тренировками, которых нет в Personal API. Каналы изолированы: если ломается web-API, чтение и статистика продолжают работать.

### 6.1 Personal API: чтение активностей

**Доступ: Garmin Connect Personal API** (решение 2). Garmin открыл его 21 октября 2026 года. Пользователь сам выпускает личный ключ и получает доступ к своим данным без заявки и без статуса организации. Источники: [Personal API](https://developer.garmin.com/gc-developer-program/personal/personal-api), [FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq/), [обзор тарифов](https://developer.garmin.com/gc-developer-program/overview/).

- **Как получить ключ.** Из этих шагов потом соберём инструкцию в приложении и в `docs/`.
  1. Войти в Garmin Connect в браузере и открыть страницу [Personal API Key](https://connect.garmin.com/app/settings/personalApiToken).
  2. Нажать Create Key и принять условия.
  3. Выбрать срок действия: 30, 90 или 180 дней либо год.
  4. Нажать Create и сразу скопировать ключ: Garmin показывает его один раз.

  Там же ключ можно удалить в любой момент. Примерно за неделю до истечения срока Garmin присылает письмо.
- **Авторизация.** Сам ключ к API не подходит, его нужно обменять на токен. Запрос `POST https://personal.connectapi.garmin.com/personalapitoken-service/personal-api/personal-api-key/token` с заголовком `Authorization: ApiKey <ключ>` возвращает OAuth2 access token. Токен живёт 24 часа или до истечения ключа, если оно наступит раньше. Refresh-токена нет: новый токен получаем тем же запросом. Ключ хранится в keychain, токен — только в памяти.
- **Что доступно.** Только чтение и только pull: Activity API (сводки в JSON и полные файлы `.FIT`), Health API, Women's Health API. Training API и Courses API, которые отправляют тренировки и маршруты в Garmin Connect, есть только в бизнес-тарифах. **Через Personal API нельзя создать или изменить тренировку в Garmin**, поэтому для тренировок есть второй канал (§6.2).
- **Условия использования.** Garmin предназначает Personal API для доступа к собственным данным и пишет, что он «not intended for commercial applications serving multiple end users». Gymgar под это подходит: каждый пользователь вводит свой ключ и видит только свои данные, общего ключа у приложения нет.
- **Ещё не проверено.** Выяснить по Swagger-документации Garmin до начала работы над `garmin`:
  - лимиты запросов;
  - на какую глубину отдаётся история;
  - есть ли в `.FIT` силовых активностей сообщения `set` с упражнением, повторами и весом. От этого зависит статистика по подходам.
- **Изоляция.** Всё, что касается ключа и токена, живёт в модуле `garmin::personal`. `sync` и слои выше просят только «активности за период».
- **Надёжность.** При ошибках и упёршись в лимиты — повтор с backoff. Если ключ истёк или удалён, пользователь видит понятное сообщение и подсказку, где выпустить новый. Загрузка инкрементальная и идемпотентная. Сырые ответы (JSON и `.FIT`) сохраняются в базе, чтобы новую статистику можно было посчитать без повторной загрузки.

### 6.2 Web-API Garmin Connect: запись тренировок

**Тренировки идут через недокументированное web-API Garmin Connect** (решение 8). Через него работает сам Garmin Connect, и через него же open-source клиенты вроде [python-garminconnect](https://github.com/cyberjunky/python-garminconnect) создают, меняют и планируют силовые тренировки. Документации и гарантий у этого API нет.

- **Риски на октябрь 2026.**
  - В марте 2026 Garmin поменял авторизацию, и библиотеку `garth`, на которой держались многие клиенты, [объявили устаревшей](https://github.com/matin/garth/discussions/222).
  - `python-garminconnect` с версии 0.3 входит по-новому: от имени iOS-приложения Garmin Connect и с запросом одноразового кода, если включена MFA.
  - На частые входы Garmin [отвечает 429](https://github.com/cyberjunky/python-garminconnect/issues/337), а некоторые User-Agent блокирует Cloudflare.

  Поток входа может снова поменяться в любой момент.
- **Только когда без него не обойтись** (решение 12). Web-API вызываем ровно для того, чего нет в Personal API: создать, изменить или удалить тренировку и прочитать её текущую версию в Garmin перед изменением. Фонового опроса нет. Всё, что умеет Personal API (активности, подходы, здоровье), читается только через него. Чем реже мы обращаемся к неофициальному API, тем меньше шанс упереться в лимиты Garmin или привлечь внимание к аккаунту.
- **Вход.** Пользователь вводит в UI логин и пароль Garmin, а при MFA — одноразовый код. Пароль нигде не хранится: после входа остаются только токены, они лежат в keychain и обновляются сами. Автоматически повторно не входим, чтобы не получить 429: если токены перестали работать, просим пользователя войти снова.
- **Изоляция.** Код web-API живёт в отдельном модуле `garmin::connect` со своей авторизацией и своими ошибками. Personal API от него не зависит. Если web-API сломается, активности, статистика и отчёты продолжат работать, а тренировки останутся в Gymgar и уйдут в Garmin, когда вход снова заработает.
- **Снимаем с живого аккаунта.** Перед реализацией записываем с настоящего аккаунта точный поток входа и формат силовой тренировки (шаги: упражнение, повторы, вес, отдых). Ответы сохраняем как очищенные fixtures. В CI настоящий Garmin не вызывается.
- **Условия.** Web-API не входит в соглашение Garmin для разработчиков. Gymgar — личный инструмент: каждый пользователь входит под своим аккаунтом.

### 6.3 Синк тренировок и конфликты

- Тренировки синхронизируются в обе стороны: созданные в Gymgar уходят в Garmin, а изменения, сделанные в Garmin Connect, возвращаются в Gymgar. Синхронизация запускается действием пользователя — сохранил или удалил тренировку, нажал «синхронизировать тренировки», — а не фоновым таймером (решение 12).
- Для каждой тренировки храним базовую версию — какой она была при последней синхронизации. Перед отправкой изменения читаем текущую версию в Garmin. Если с тех пор тренировку изменили и в Gymgar, и в Garmin, это конфликт. Пользователь выбирает версию на отдельном экране (решение 6), автоматически ничего не перезаписывается.
- **Корзина** (решение 11). Перенос тренировки в корзину сразу удаляет её из Garmin, поэтому она пропадает и с часов. Восстановление загружает её в Garmin заново, уже под новым id. Если Garmin недоступен, операция ждёт в очереди и повторяется при следующей синхронизации; в Gymgar тренировка уже в корзине.

## 7. MCP

- Инструменты генерируются из реестра: `command_list`, `command_run`, `command_batch`. Рядом лежат curated-инструменты для частых сценариев (список тренировок, тренировка целиком, статистика прогресса) и ресурсы вроде `gymgar://workouts`.
- **Headless** (`gymgar-cli mcp`, stdio) поднимает собственную `Session` на том же хранилище. **Bridge** подключается к запущенному приложению по loopback TCP с токеном. Если приложение запущено, CLI работает через bridge, чтобы в хранилище не было двух писателей. Как именно CLI это определяет, решим при реализации.
- **Экспорт.** Через MCP отчёты пишутся только в каталог, который пользователь разрешил заранее; так photocraft ограничивает файлы через `AuthorizedWorkspace`.
- **Безопасность.** У команд есть флаг доступности агенту. Только из UI доступны ввод ключа, вход в Garmin и очистка корзины. Агент может переносить записи в корзину, но не удалять их навсегда. Секреты не попадают в ответы. Неизвестные аргументы отклоняются. Паника внутри инструмента превращается в ошибку инструмента, а сервер продолжает работать.

## 8. Решения

Решения приняты 2026-10-23.

| # | Вопрос | Решение | Следствия |
|---|---|---|---|
| 1 | Хранилище | SQLite | `rusqlite` с фичей `bundled`, режим WAL. Миграции версионируются через `PRAGMA user_version`. Каждая мутация — транзакция. Писатель один — приложение: если оно запущено, CLI работает через bridge |
| 2 | Доступ к Garmin | Personal API с личным ключом пользователя | Подробно в §6. В приложении и в `docs/` будет инструкция со ссылкой на страницу выпуска ключа. Ключ хранится в keychain. Personal API только читает данные |
| 3 | Объём v1 | Создание и редактирование тренировок; просмотр выполненных активностей; статистика, графики и отчёты | Тренировки хранятся в базе Gymgar и синхронизируются с Garmin (решение 8), активности загружаются из Garmin. Отчёты — решение 9 |
| 4 | Язык UI | Английский и русский | Строки обёрнуты в `tl!()`. Каталоги: `en` (исходный) и `ru`. Для русского есть формы множественного числа one/few/many. Язык выбирается в настройках: системный, English или Русский. Тест проверяет, что каталог `ru` полный. Id команд, MCP и логи — на английском |
| 5 | Undo | Не делаем; возможно, он вообще не понадобится | Мутация выполняется одной транзакцией. Разрушительные команды подтверждаются в UI и помечаются для MCP как destructive. От ошибок защищает корзина (решение 10) |
| 6 | Конфликты синка | Ручное разрешение | Действует для тренировок, потому что они синхронизируются в обе стороны (§6.3): храним базовую версию, сравниваем три стороны, пользователь выбирает на отдельном экране. Активности только читаются, у них конфликтов нет |
| 7 | Лицензия и публичность | Публичный репозиторий [alekseinovikov/gymgar](https://github.com/alekseinovikov/gymgar), `MIT OR Apache-2.0` | — |
| 8 | Как тренировка попадает в Garmin | Через недокументированное web-API Garmin Connect, без файлов: всё делается в одном приложении | §6.2 и §6.3. Путь хрупкий, поэтому код живёт в отдельном модуле `garmin::connect`. Если он сломается, остальное приложение продолжит работать. Пароль не хранится, хранятся только токены в keychain |
| 9 | Отчёты | Графики внутри приложения и экспорт в CSV, HTML и PDF | Отчёт — модель данных, которую строит engine. Её рисуют несколько рендереров: в приложении — `egui_plot`, для экспорта — крейт `report` (L1, появится вместе с фичей). Графики описываются одной спецификацией, чтобы в приложении и в файлах они выглядели одинаково. HTML самодостаточный: стили и SVG-графики лежат внутри файла. PDF использует те же SVG-графики. Через MCP файлы пишутся только в разрешённый каталог |
| 10 | Удаление | Корзина | Удаление переносит запись в корзину (`deleted_at`): из списков и статистики она пропадает, вернуть её можно командой восстановления. Очистка корзины удаляет навсегда: в UI она подтверждается, агенту недоступна. Агент может только переносить в корзину. Автоочистки нет |
| 11 | Тренировка в корзине и Garmin | Сразу удаляем её из Garmin; восстановление загружает её заново | §6.3. Удалённая тренировка сразу пропадает с часов. Если Garmin недоступен, удаление ждёт в очереди |
| 12 | Каналы Garmin | Оба: Personal API читает, недокументированное web-API — только для редких необходимых действий | §6. Через web-API только создаём, меняем и удаляем тренировки и читаем их текущую версию перед изменением, без фонового опроса. Пользователь один раз вводит ключ (на срок до года) и один раз входит в аккаунт. Если web-API сломается, статистика и отчёты продолжат работать |
